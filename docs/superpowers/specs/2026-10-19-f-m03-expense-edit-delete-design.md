- 기준 문서: `docs/00-renewal-development-guide.md`(우선), `docs/02-requirements-features.md` F-M03, `docs/03-user-flow.md` 2절, `docs/api-spec.md` 지출 API

## 1. 목표와 범위

사용자가 이번 달 내역에서 지출을 눌러 금액·날짜·카테고리·메모를 고치거나 지우면, 내역과 홈의 사용 금액·사용률·잔액·펫 상태가 바뀐다.

**쓰임새(사용자 확인)**

- 금액을 잘못 쳤을 때: 기록 직후 같은 달에 바로 고친다.
- 며칠 뒤 환불받았을 때: 일부 환불은 금액을 줄이고, 전체 환불은 삭제한다. 별도 환불 기록은 만들지 않는다(문서 기준).

**포함**

- 이번 달 내역의 행을 누르면 수정 화면으로 이동
- 수정 화면: 기존 값을 채운 입력 칸, 바뀐 필드만 `PATCH`, 아래쪽 삭제와 확인
- 저장·삭제 뒤 이번 달 내역과 홈 다시 조회(기존 포커스 조회 재사용)

**제외(사용자 결정)**

- **지난달 이전 지출의 수정·삭제.** 들어갈 화면이 없다. F-M05 통계 화면의 전체 내역에서 이 수정 화면으로 연결한다.
- **날짜를 다른 달로 옮기는 수정.** 이번 작업에서는 수정 화면의 날짜를 이번 달 1일 ~ 오늘(서울 기준)로 막는다. "새 날짜의 월 목록으로 이동"·"이전 월과 새 월 모두 갱신"은 F-M05에서 날짜 제한을 풀 때 함께 구현한다.
- 데이터 캐시 라이브러리. 기존처럼 포커스 시 다시 조회한다.

**실패로 보는 것**

- 아무것도 안 바꿨는데 저장되어 요청이 나가는 것
- 카테고리 `null`처럼 서버가 400으로 막는 값을 보내는 것
- 확인 없이 삭제되는 것
- 이미 지워진 지출에서 연결 오류처럼 보이는 안내

## 2. 백엔드 확인 결과 (2026-10-19, `bootTestRun`)

`api-spec.md`와 실제 응답이 일치한다.

| 요청 | 응답 |
|---|---|
| `GET /expenses/{id}` | 200 지출 객체 |
| `PATCH /expenses/{id}` `{"amount":7000,"memo":null}` | 200, 금액 변경·메모 삭제, 나머지 유지 |
| `PATCH` `{"category":null}` | 400 `INVALID_REQUEST`, `fields: [{field: "category"}]` |
| `DELETE /expenses/{id}` | 204, 본문 없음 |
| 삭제 뒤 `GET`·`PATCH` | 404 `EXPENSE_NOT_FOUND` |

## 3. 구조

새 의존성은 없다.

```
src/app/
  _layout.tsx                (수정) ready guard에 expenses/[id] 추가, 헤더 "지출 수정"
  expenses/index.tsx         (수정) 행 누르면 router.push(`/expenses/${id}`)
  expenses/new.tsx           (수정) 입력 칸을 ExpenseForm으로 옮김. 동작은 그대로
  expenses/[id].tsx          수정 화면
src/components/
  expense-form.tsx           금액·날짜·카테고리·메모 입력 칸과 칸별 오류 표시(입력·수정 공유)
  expense-row.tsx            (수정) onPress를 받아 Pressable로 감싼다
src/api/
  types.ts                   (추가) ExpenseUpdate = Partial<NewExpense>
  client.ts                  (추가) getExpense(id), updateExpense(id, body), deleteExpense(id). PATCH·DELETE 메서드, 204 본문 없음 처리
src/lib/
  expense.ts                 (추가) 바뀐 필드만 담은 PATCH 본문 계산
  month.ts                   (추가) 이번 달 1일(서울 기준)
```

입력 화면과 수정 화면의 차이는 각 화면이 정한다. `ExpenseForm`은 값·변경 콜백·칸별 서버 오류·날짜 범위·카테고리 해제 허용 여부를 받는 표시 컴포넌트다. 저장 버튼·요청·화면 전체 오류는 화면에 둔다. 나누는 정확한 경계는 구현자 판단.

## 4. 화면 이동과 데이터 흐름

```
홈 ──"이번 달 내역 보기"──▶ 이번 달 내역 ──행 누름──▶ 지출 수정(expenses/[id])
                               ▲                         │
                               └──── 저장·삭제 성공 ─────┘ router.back()
```

- 수정 화면은 들어올 때 `GET /expenses/{id}`로 최신 값을 불러온다. 목록 항목을 넘겨받아 쓰지 않는다(다른 곳에서 바뀌었을 수 있음).
- 저장·삭제 성공 뒤 `router.back()`. 이번 달 내역과 홈은 이미 포커스 시 다시 조회하므로 커서를 버리고 첫 페이지부터 다시 불러온다(커서 규칙 충족). 추가 갱신 코드는 없다.
- 홈에는 지출 행이 없으므로 수정 진입점은 이번 달 내역뿐이다.

## 5. 수정 화면 (`expenses/[id]`)

헤더 "지출 수정", 뒤로 가기 "뒤로".

### 불러오기

| 결과 | 표시 |
|---|---|
| 로딩 중 | 가운데 로딩 |
| 200, 날짜가 이번 달 | 기존 값으로 채운 폼 |
| 200, 날짜가 이번 달이 아님 | "지난달 지출은 아직 고칠 수 없어요" + "내역으로" (자정에 달이 바뀐 직후 목록에서 들어온 경우. 내 판단) |
| 404 `EXPENSE_NOT_FOUND` | "이미 삭제된 지출이에요" + "내역으로" |
| 네트워크 오류·500 | 연결 오류 문구 + "다시 시도" |

"내역으로"는 `router.back()`.

### 입력 칸

입력 화면과 같은 칸·검증·문구를 쓴다. 차이만 적는다.

- 금액: 기존 금액을 쉼표 형식으로 채운다.
- 날짜: 기존 날짜. 선택 범위는 **이번 달 1일 ~ 오늘(서울 기준)**.
- 카테고리: 기존 카테고리가 선택된 상태. **선택한 칩을 다시 눌러도 해제되지 않는다**(수정에서 `null`은 400). 다른 칩을 누르면 바뀐다.
- 메모: 기존 메모(없으면 빈칸). 비우거나 공백만 남기면 메모 삭제(`memo: null`).

### 저장

- 불러온 값과 비교해 **바뀐 필드만** `PATCH` 본문에 담는다. 메모는 입력값을 `parseMemo`로 정리한 값(공백만 → `null`)을 불러온 메모와 비교한다.
- 저장 버튼은 금액이 유효하고, 메모가 100자 이하이고, **바뀐 필드가 하나 이상일 때만** 활성. 저장 중 로딩·비활성, 중복 요청 없음.

| 결과 | 처리 |
|---|---|
| 200 | `router.back()` |
| 400 `fields` | 해당 칸 아래 서버 메시지, 입력 유지 |
| 404 `EXPENSE_NOT_FOUND` | 폼 대신 "이미 삭제된 지출이에요" + "내역으로" |
| 네트워크 오류·500 | 저장 버튼 위 연결 오류 문구, 입력 유지 |

### 삭제

- 저장 버튼 아래에 빨간 글씨 "삭제" 버튼.
- 누르면 기기 기본 확인창(`Alert.alert`): 제목 "이 지출을 삭제할까요?", 버튼 "취소"·"삭제"(destructive). 취소하면 아무 일도 없다.
- 삭제 요청 중에는 저장·삭제 모두 비활성.

| 결과 | 처리 |
|---|---|
| 204 | `router.back()` |
| 404 `EXPENSE_NOT_FOUND` | 이미 지워진 것이므로 성공과 같이 `router.back()` (내 판단) |
| 네트워크 오류·500 | 저장 버튼 위 연결 오류 문구, 화면 유지 |

## 6. 이번 달 내역 (변경)

- 행 전체가 눌린다(`accessibilityRole="button"`, 접근성 이름에 제목·금액 포함). 누르면 `/expenses/{id}`.
- 나머지 동작은 그대로.

## 7. API 클라이언트

- `getExpense(id)`: `GET /expenses/{id}`
- `updateExpense(id, body)`: `PATCH /expenses/{id}`, 본문은 바뀐 필드만
- `deleteExpense(id)`: `DELETE /expenses/{id}`, 204 본문 없음
- 지금 `request`는 성공 응답마다 `res.json()`을 부른다. 204에서는 본문을 읽지 않게 바꾼다.
- 401 처리(갱신 후 재시도)는 기존 `request`를 그대로 탄다.

## 8. 테스트

| 대상 | 경우 |
|---|---|
| `lib/expense` PATCH 본문 계산 | 변경 없음 → 빈 본문; 금액만; 날짜만; 카테고리만; 메모 추가·변경; 메모 비움·공백만 → `memo: null`; 원래 메모 없음 + 빈칸 → 변경 없음 |
| `lib/month` | 이번 달 1일(UTC 15:00 경계) |
| `api/client` | 세 요청의 메서드·경로·본문; 204에서 본문을 읽지 않음; PATCH 401 → 갱신 후 재시도 |
| 수정 화면 | 불러온 값 채움; 변경 없으면 저장 비활성; 바뀐 필드만 PATCH; 카테고리 칩 해제 안 됨; 400 필드 메시지·입력 유지; 404(불러오기·저장) 안내; 불러오기 실패·다시 시도; 이번 달이 아닌 지출 안내; 저장 두 번 눌러도 요청 1번; 삭제 확인 취소 → 요청 없음; 삭제 확인 → DELETE 후 back; 삭제 404 → back; 삭제 실패 → 문구·화면 유지 |
| 지출 입력 화면 | 폼 분리 뒤 기존 테스트 그대로 통과 |
| 이번 달 내역 화면 | 행 누르면 `/expenses/{id}`로 이동 |
