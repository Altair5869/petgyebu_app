# 지출 등록 중복 방지 설계: Idempotency-Key

- 작성일: 2026-10-21
- 브랜치: 앱 `feature/F-M03-expense-idempotency`, 백엔드 `feature/F-M03-expense-idempotency`(둘 다 `develop`에서 분기)
- 관련 기능: F-M03(수동 지출) 중 지출 생성
- 기준 문서: `docs/00-renewal-development-guide.md`(우선), `docs/api-spec.md` 지출 API
- 진행 방식: 사용자가 질문 없이 진행하라고 했다("그냥 진행해"). 아래 결정은 모두 내 결정이다.

## 1. 문제와 목표

앱은 요청마다 10초 제한을 둔다. 지출 등록이 시간 초과되면 서버에는 이미 저장됐을 수 있다. 지금은 "저장됐는지 확인하지 못했어요. 월별 통계에서 확인해 주세요."라고 안내만 한다. 사용자가 다시 저장을 누르면 같은 지출이 두 번 기록된다. 시간 초과 외에 연결이 끊긴 경우도 같다.

**목표**: 같은 입력으로 다시 저장해도 지출이 한 번만 기록된다. 다시 저장해도 안전하므로, 시간 초과 안내는 "다시 저장해도 된다"로 바꾼다.

**포함**

- 백엔드: `POST /expenses`의 선택 헤더 `Idempotency-Key`, DB 마이그레이션, 테스트, 문서(`00` 가이드 API 절)
- 앱: 지출 등록 요청마다 키를 보내고, 같은 입력의 재시도에는 같은 키를 쓴다. 시간 초과·충돌 문구를 바꾼다
- 앱 `docs/api-spec.md` 갱신
- Maestro `expenses/request-timeout.yaml`을 "멈춘 서버 → 시간 초과 → 서버 재개 → 다시 저장 → 한 건만"으로 바꾼다

**제외**

- 지출 수정(PATCH)·삭제(DELETE): 같은 요청을 두 번 보내도 결과가 같아서 키가 필요 없다
- 예산 PUT: 같은 이유로 제외한다
- 키 만료·정리 작업: 키는 지출 행에 붙어 있어 지출과 함께 사라진다
- 오래된 앱 빌드 호환을 위한 별도 처리: 헤더가 선택이므로 키 없는 요청은 지금처럼 동작한다

**실패로 보는 것**

- 시간 초과 뒤 같은 입력으로 다시 저장했는데 두 건이 생기는 것
- 다른 입력(금액을 고친 뒤 저장)이 이전 키 때문에 거부되거나 이전 지출로 처리되는 것
- 다른 사용자의 같은 키 값이 서로 영향을 주는 것

## 2. 계약 (백엔드가 기준, 앱 `api-spec.md`도 같이 갱신)

`POST /api/v1/expenses`

- 요청 헤더 `Idempotency-Key`(선택): UUID 문자열(대소문자 무관, 표준 36자 형식). 형식이 틀리면 `400 INVALID_REQUEST`, `fields: [{ field: "Idempotency-Key", ... }]`
- 헤더가 없으면 지금과 같다(201, 매번 새 지출)
- 헤더가 있고 같은 사용자·같은 키의 지출이 **없으면** 새로 만들고 201
- 헤더가 있고 같은 사용자·같은 키의 지출이 **있으면**
  - 요청 본문(검증·정규화 후 `amount`, `expenseDate`, `category`, `memo`)이 그 지출과 같으면 새로 만들지 않고 **200**과 기존 지출을 돌려준다
  - 다르면 **409 `IDEMPOTENCY_KEY_REUSED`**(새 오류 코드)
- 본문 검증(400)은 키 조회보다 먼저 한다
- 동시에 같은 키로 두 요청이 들어와도 한 건만 생긴다. 하나는 201이고, 다른 하나는 위 규칙대로 200 또는 409다
- 키는 사용자별이다. 다른 사용자의 같은 키와 섞이지 않는다
- 지출을 삭제하면 그 키도 함께 사라진다. 이후 같은 키로 오면 새로 만든다(201)
- 지출을 수정한 뒤 원래 내용으로 같은 키가 다시 오면 내용이 달라졌으므로 409다. 앱의 재시도는 등록 화면 안에서만 일어나므로 실제로는 생기지 않는다

DB(Flyway `V2`): `expenses.idempotency_key UUID NULL`. 유니크 부분 인덱스 `(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`.

## 3. 앱 동작

- `api.createExpense(body, idempotencyKey: string)`: `Idempotency-Key` 헤더를 붙여 보낸다. 201과 200 모두 성공으로 처리한다(기존 `res.ok`).
- 키 생성: `expo-crypto`의 `randomUUID()`. Expo 권장 모듈이지만 네이티브 모듈이라 개발용 앱을 다시 빌드해야 한다. 구현 전에 SDK 58 문서로 확인하고 `npx expo install`로 설치한다.
- 등록 화면은 **마지막으로 보낸 입력**과 그 키를 기억한다.
  - 같은 입력으로 다시 저장하면 같은 키를 쓴다.
  - 입력(금액·날짜·카테고리·메모 중 하나라도)이 바뀐 뒤 저장하면 새 키를 만든다.
  - 화면을 새로 열면 새 키로 시작한다.
- 문구
  - 시간 초과: `'저장됐는지 확인하지 못했어요. 다시 저장해도 한 번만 기록돼요.'`(`SAVE_UNCONFIRMED` 교체)
  - 409 `IDEMPOTENCY_KEY_REUSED`: `'이미 저장된 기록과 내용이 달라요. 월별 통계에서 확인해 주세요.'`. 앱은 입력이 바뀌면 키를 바꾸므로 정상적으로는 생기지 않는다
  - 그 밖의 오류는 지금처럼 `errorMessage()`를 쓴다
- 수정·삭제 화면의 시간 초과 문구(`UPDATE_UNCONFIRMED`·`DELETE_UNCONFIRMED`)는 그대로 둔다

## 4. 검증

**백엔드**(`./gradlew test --no-daemon`, Testcontainers)

- 키 없이 두 번 등록하면 두 건(기존 동작)
- 같은 키·같은 본문 두 번이면 201 다음 200, 같은 id, DB에 한 건
- 같은 키·다른 본문이면 409 `IDEMPOTENCY_KEY_REUSED`
- 잘못된 키 형식이면 400 `Idempotency-Key`
- 다른 사용자의 같은 키는 각자 201
- 삭제 뒤 같은 키면 201로 새로 생성
- 동시 같은 키 요청(두 스레드)이면 한 건만 생기고 둘 다 200·201 중 하나
- 카테고리 생략과 `OTHER` 명시, 메모 생략과 `null`은 정규화 뒤 같은 본문으로 본다

**앱**(Jest)

- `createExpense`가 `Idempotency-Key` 헤더를 보낸다
- 등록 화면: 같은 입력으로 두 번 저장 시도하면(첫 번째 시간 초과) 같은 키, 금액을 바꾼 뒤 저장하면 다른 키
- 문구: 시간 초과 시 새 문구, 409 시 충돌 문구

**시뮬레이터**(`bootTestRun`, Maestro)

- `request-timeout.yaml` 갱신: 백엔드를 `kill -STOP`으로 멈춘 상태에서 저장 → 10초 뒤 새 문구 → `kill -CONT`로 재개(멈춘 동안 쌓인 첫 요청이 저장됨) → 다시 저장 → 월별 통계에서 그 금액이 **한 건**. Maestro가 서버를 멈추고 재개할 수는 없으므로 준비·중간 단계는 README대로 손으로 하거나, 플로우를 둘로 나누고 그 사이에 명령을 실행한다
- 기존 `expenses/record-and-list.yaml` 회귀

**필수 검사**: 앱 `npm run lint`, `npm run typecheck`, `npm test`, `npx expo export --platform ios`. 백엔드 `./gradlew test --no-daemon`.

## 4-1. 진행 순서

백엔드 PR을 먼저 `develop`에 병합한다. 앱 PR은 병합된 백엔드 커밋을 적고 그 백엔드로 확인한다. 헤더가 선택이라 순서가 바뀌어도 깨지지는 않는다.
