- 작성일: 2026-10-28
- 브랜치: `feature/F-M07-weekly-insights`
- 관련 기능: F-M07(소비 인사이트) 앱 화면 `APP-006`. 진입점은 F-M06(현재 월 홈)
- 백엔드: `petgyebu_backend_renewal` develop `52aa2b0`(`M-011`, PR #38). 백엔드 변경 없음
- 기준 문서: `docs/00-renewal-development-guide.md`(우선). 앱 저장소의 문서에는 아직 F-M07이 없으므로 이 작업에서 백엔드 문서와 맞춘다(6절)

## 1. 목표와 범위

사용자는 **주말에 한 주 지출을 돌아볼 때**(사용자) 이 화면을 연다. 지난주보다 어디에 더 썼는지와, 이 속도로 쓰면 이번 달 예산이 어떻게 될지를 한 화면에서 본다.

**포함**

- 홈에서 들어가는 새 화면 "이번 주 돌아보기": 예산 예측 문장, 이번 주 요약 문장, 카테고리별 이번 주·지난주 막대 비교
- `GET /api/v1/insights` 연결(API 클라이언트·타입)
- 앱 문서에 F-M07·인사이트 API 반영

**제외**

- 푸시 알림(MVP 밖), 과거 주 넘겨 보기(API가 오늘 기준만 제공), 차트 라이브러리(막대는 기본 `View`)
- 앱에서 주 범위·예측을 다시 계산하는 것. 서버 값을 그대로 쓴다

**실패로 보는 것**

- 서버가 준 정렬·금액과 다른 값이 보이는 것(앱에서 재정렬·재계산)
- `TOO_EARLY`·`BUDGET_REACHED`·`NO_BUDGET`에서 날짜나 하루 평균 자리에 `null`·`0`·빈칸이 보이는 것
- 지출이 없는데 빈 막대 칸이나 "0원 더 썼어요" 같은 문장이 보이는 것
- 지출을 바꾸고 돌아왔는데 예전 숫자가 그대로 있는 것

## 2. 백엔드 확인 결과 (2026-10-28, `bootTestRun`, 오늘 = 10월 28일 화요일)

| 경우 | 응답 요지 |
|---|---|
| 새 계정(펫·예산 없음) | 200, `categories: []`, `forecast: {status: NO_BUDGET, dailyAverageAmount: null, exhaustionDate: null}` |
| 예산 300,000원, 지출 0건 | `WITHIN_BUDGET`, `dailyAverageAmount: 0`, `exhaustionDate: null` |
| 이번 주 카페 21,000·식비 12,000·교통 5,000, 지난주 카페 8,000·식비 16,000·교통 5,000, 예산 300,000 | `thisWeek {2026-10-26, 2026-10-28}`, `lastWeek {2026-10-19, 2026-10-21}`, categories 순서 CAFE(+13,000) → TRANSPORT(0) → FOOD(−4,000), `WITHIN_BUDGET`, 하루 평균 2,392 |
| 같은 지출, 예산 70,000 | `WILL_EXHAUST`, 하루 평균 2,392, `exhaustionDate: 2026-10-30` |
| 같은 지출, 예산 60,000 | `BUDGET_REACHED`, 나머지 `null` |
| 지난주 식비 9,000만 있음 | categories `[FOOD: this 0, last 9000, change −9000]` |
| 토큰 없음 | 401 `UNAUTHORIZED` |

붙여 받은 계약·백엔드 `00` 8절과 일치한다. `TOO_EARLY`는 1~3일에만 나오므로 오늘은 실제 응답으로 확인하지 못했다(Jest로 문구를 검증한다).

## 3. 화면 이동

```
홈 ──"이번 주 돌아보기"──▶ 이번 주 돌아보기 ──뒤로──▶ 홈
```

- 홈의 "월별 통계 보기 →" 링크 바로 아래에 같은 모양의 "이번 주 돌아보기 →" 링크를 둔다(사용자 결정: 홈에 따로 링크).
- 새 라우트(파일 위치·이름은 구현자 판단, 예: `src/app/insights.tsx`)를 `stage === 'ready'` 보호 그룹에 추가한다. 헤더 표시, 제목 "이번 주 돌아보기", 뒤로 라벨 "뒤로"(다른 화면과 같음).

## 4. 화면 (C안 + B안 막대, 사용자 선택)

한 번에 스크롤되는 화면. 위에서 아래로:

### 4-1. 예측 카드 (강조 배경 `colors.secondary`)

| `status` | 큰 문장 | 작은 줄 |
|---|---|---|
| `WILL_EXHAUST` | "이 속도면 10월 30일에 예산을 다 써요" | "하루 평균 2,392원" |
| `WITHIN_BUDGET` | "이 속도면 이번 달 예산 안에서 지낼 수 있어요" | "하루 평균 2,392원"(지출 0이면 "하루 평균 0원") |
| `BUDGET_REACHED` | "이번 달 예산을 모두 썼어요" | 없음 |
| `TOO_EARLY` | "4일부터 이번 달 예측을 보여 드려요" | 없음 |
| `NO_BUDGET` | "이번 달 예산이 없어 예측할 수 없어요" | 없음 |

- 날짜는 `exhaustionDate`(`YYYY-MM-DD`)의 월·일을 앞 0 없이 쓴다("10월 30일"). 금액은 기존 `formatWon`.
- 문구는 사용자와 합의한 그대로다. 홈에 들어온 사용자는 현재 월 예산이 있어 `NO_BUDGET`은 드물지만 문구를 둔다.
- 알 수 없는 `status` 값은 타입상 없지만, 들어오면 예측 카드를 숨긴다(내 판단, 화면 전체를 오류로 만들지 않음).

### 4-2. 이번 주 요약 문장 (흰 카드)

`categories`가 비어 있지 않을 때만 보인다. 서버 정렬을 그대로 쓰고 **첫 항목**만 본다.

- 첫 항목 `changeAmount > 0`: "이번 주에는 지난주보다 **카페**에 **13,000원** 더 썼어요" (카테고리 이름 굵게, 금액 굵게·빨강)
- 그 외(모두 0 이하): "이번 주에는 지난주보다 늘어난 지출이 없어요"

### 4-3. 카테고리별 변화 카드 (흰 카드)

- 제목 "카테고리별 변화", 그 아래 날짜 범위 "10월 26일~28일 vs 10월 19일~21일".
  - 범위 표기: 같은 달이면 "M월 D일~D일", 달이 다르면 "M월 D일~M월 D일", 하루면 "M월 D일"(월요일). 범위는 `thisWeek`·`lastWeek`를 그대로 쓴다.
- 행마다: 카테고리 이름 | 막대 두 개(위: 이번 주, 카테고리 색 `CATEGORY_COLORS`; 아래: 지난주, `colors.border` 회색) | 변화량.
  - 막대 길이: 이 화면의 모든 `thisWeekAmount`·`lastWeekAmount` 중 최댓값을 100%로 한 비율(내 판단). 0원이면 막대 없음(길이 0).
  - 변화량: 양수 "+13,000"(빨강), 음수 "−4,000"(초록), 0은 "0"(회색 `colors.muted`). "원"은 붙이지 않는다(시안 그대로). 빨강은 `colors.danger`, 초록은 시안의 `#4E7A48`(사용자 결정: 시안 색 그대로).
  - 행 순서는 서버 순서 그대로.
- 카드 맨 아래 범례 "색 막대 이번 주 · 회색 막대 지난주".
- 접근성: 각 행을 하나로 묶어 읽는다. 예: "카페, 이번 주 21,000원, 지난주 8,000원, 13,000원 늘었어요" / "…4,000원 줄었어요" / "…변화 없어요"(내 판단).

### 4-4. 빈 상태

`categories: []`이면 4-2·4-3 대신 흰 카드에 "이번 주와 지난주에 기록한 지출이 없어요". 예측 카드는 그대로 보인다.

### 4-5. 로딩·오류·갱신

- 월별 통계 화면과 같은 방식: 불러오는 중 `ActivityIndicator`, 실패하면 `CONNECTION_ERROR` 문구와 "다시 시도" 버튼.
- 화면에 들어올 때와 돌아올 때마다(`useFocusEffect`) 다시 불러온다. 늦게 온 이전 응답은 버린다(`useMonthStats`의 세대 방식과 같음).
- 401은 기존 API 클라이언트의 토큰 갱신·세션 만료 처리를 그대로 탄다(새 처리 없음).
- 월요일에 변화 폭이 크게 보이는 문제는 따로 안내하지 않고 날짜 범위만 보여 준다(사용자 합의).

## 5. 코드 구조 (구현자 판단, 기존 패턴 따름)

- `src/api/types.ts`: `Insights`, `WeeklyCategoryChange`, `ForecastStatus` 등 타입. `forecast`는 세 키가 항상 있고 값이 `null`일 수 있다.
- `src/api/client.ts`: `getInsights: () => request<Insights>('GET', '/insights')`.

- 화면 구성 요소는 `src/components/`에 둔다. 카테고리 이름·색은 `CATEGORY_LABELS`·`CATEGORY_COLORS`를 재사용한다.

## 7. 검증

- Jest(`__tests__/`):
  - 예측 문구: 다섯 상태 각각, 날짜 "10월 30일"(앞 0 없음, 예: `2026-11-05` → "11월 5일"), 하루 평균 0원.
  - 요약 문장: 첫 항목 양수 / 0 / 음수만 / 빈 배열.
  - 날짜 범위 표기: 같은 달, 달 걸침(10-26~11-01), 하루(월요일).
  - 막대 비율: 최댓값 기준, 0원.
  - 화면: 로딩 → 표시, 오류 → 다시 시도, 빈 상태, 홈의 링크로 이동.
  - API 클라이언트: `GET /insights` 경로와 인증 헤더.
- `npm run lint`, `npm run typecheck`, `npm test` 통과.
- iOS 시뮬레이터 + `bootTestRun`: Maestro 시나리오 추가(예: `.maestro/insights/weekly-insights.yaml`). 새 계정에서 지출을 기록한 뒤 홈 → "이번 주 돌아보기" → 요약 문장·카테고리·예측 문장이 보이는지 확인. 예측 상태는 실행 날짜(1~3일이면 `TOO_EARLY`)에 따라 달라지므로 시나리오는 날짜에 덜 묶이는 확인(예: 요약 문장, 카테고리 이름)을 중심으로 하고, 예측 카드는 존재만 확인한다(내 판단).
- 실행하지 않은 확인(Android 등)은 PR에 미확인으로 적는다.
